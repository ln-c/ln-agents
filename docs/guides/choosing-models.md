# Choosing models

`/models` shows the catalog. `/agents` shows each agent slot (`design.proposal_b.primary`, `build.primary`, `human_authority.model_assistance`, ...), the model it is bound to, where that runs and which operations it serves. Three commands change that, in design mode:

- `/add_model <provider> <model_id> [capability ...]` adds a model to the catalog. Its family comes from the provider's `family_patterns`, never from what you type. A model the catalog already has (same provider and id) is not added twice: the capabilities you name are claimed for it, which is how a known but unclaimed model becomes bindable. A provider that starts one fixed server (`launch`, the llama.cpp ones) is refused: that is an edit to its launch. A capability is a claim you make, not a measurement; `models test --model M` checks it once the model is bound.
- `/remove_model <model>` removes a model that nothing is bound to, and that is not the coordinator named in `LN-AGENTS.md`.
- `/agents <slot> <model>` binds a slot to a model. A list slot (`model_assistance`) takes several, separated by commas. A slot that holds a non-model (`deterministic_orchestrator`) is not rebound.
- `/agents auto [what you want]` asks the authority to propose bindings, for example `/agents auto use only local models for build`. The authority is the model `LN-AGENTS.md` names as `coordinator` (or its `fallback`), and only if `policy/model_registry.yaml` binds it to `human_authority`, whose `model_assistance` list is the list of models allowed to act as the authority. It reads the catalog and the slots as data and the human-authority spec as reference, replies with one JSON object, and may only name existing slots and catalog models: it cannot add a model, claim a capability or change anything else. This is the one command here that calls a model.

**An agent with no model.** Registry rule R20 says every `agents/*.md` has a model, so a spec file added to `agents/` (a plugin update, or your own) with no entry in the registry, or an entry whose spec names no model, leaves an agent without one. Then `/start` starts nothing. It lists the agents and proposes one change that gives each of them a model, with the diff and which of them would send data off this host. **The authority chooses**: the model `LN-AGENTS.md` names as coordinator (or its fallback), if the registry binds it to `human_authority` and it is ready, acting as the human authority, is shown the catalog and the brief of each agent's spec (not the whole file) and names one catalog model for each, with a reason. Code writes the draft from those names; the model writes no YAML. Its answer is used only if it names every agent that has no model, once, with catalog models, and the registry rules accept the result; a partial answer is never completed with code's picks. Otherwise, and when no model can act as the authority (`human_authority` is itself one of the agents with no model, the coordinator is not bound to it, it is not ready, or a spec has no brief), code gives each agent the coordinator, the reply says it was made by code, and says why the authority was not used. No model is called before the cheap checks pass. Asking `/start` again while that draft waits shows it again and does not ask a model again; `/discard` it to get a new proposal. You `/confirm` it, then `/start` again, and `/agents` changes any binding afterwards. When every agent already has a model, `/start` starts as it always did, with no extra step.

The edit follows two rules. An entry that exists gets the model as `model_assistance` and keeps its `primary`: `human_authority` is a human, and `exception_router` is deterministic, so a model never becomes either. A spec that no entry owns gets a new entry, `<name>: {spec, primary}`, named after its file (`pipeline-foo-bar-agent.md` is `foo_bar`); it has no stage wiring, so it serves no operation until a human declares one. Without a coordinator in `LN-AGENTS.md` (or with one that is not in the catalog) nothing is proposed, and the reply says to name one. While an agent has no model `/add_model`, `/remove_model`, `/agents <slot> <model>` and `/agents auto` are refused too (every draft is validated against the whole repository, and `/agents auto` reads the strict catalog, which refuses a repository that fails R20); the refusal says to run `/start`. Two spec files that would get the same name (`pipeline-foo-agent.md` and `foo.md`) are refused with both file names. Asking again does not pile up drafts. The readiness check behind the authority and behind `/models` tolerates the R20 gaps and nothing else (any other violation still stops them, and the check that keeps a run from starting is unchanged), so `/models` and `/agents` keep working while an agent has no model: each begins with the agents that have none and the way on (`/start`, then `/confirm`), then shows the catalog or the mapping as usual; `/agents` also adds a row to its table for each agent with no model, since such an agent has no slot to list.

Each command only drafts. Code builds the new text from the command's own fields (for `/agents auto`, from the bindings the authority named, after checking each), parses it and checks that it holds exactly the registry meant, then validates the whole repository with it: R14 independence, R18 capabilities, R17 families, R20 specs and the rest. A change that would break a rule is refused with the rule's own message and nothing is stored. Otherwise the reply shows a diff and an id, and nothing in `policy/` has changed yet. **`/confirm <id>` writes it**, and only you can type that: no reply from a model is ever run as a command. The file is edited as text, so its comments and layout stay. A draft is dropped with `/discard <id>`, and is refused when the registry has changed since it was made.

A confirmed change is an edit to your working tree, not a commit. You review it with `git diff` and commit and push it signed, like any change to policy, and it is covered by CODEOWNERS when it comes in as a pull request. A run keeps the policy it froze at its start, so a change affects only the runs you start afterwards. The bearer token protects this path (whoever holds it can draft and confirm), as it protects every A2A skill.
